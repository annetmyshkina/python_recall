Python Recall — Personal AI Learning System
Версия документа: 2.0
Тип проекта: Personal Learning Management System
Основное назначение: персональное изучение и повторение Python с использованием интервального обучения и AI-наставника.
1. Цель проекта
Разработать персональное веб-приложение для систематизации знаний по Python, создания собственных учебных карточек, интервального повторения и анализа уровня усвоения материала.

Система должна не просто хранить вопросы и ответы, а помогать пользователю:
- закреплять изученные концепции;
- проверять понимание материала;
- выявлять пробелы в знаниях;
- находить ошибки и неточности в собственных объяснениях;
- улучшать качество учебных карточек;
- получать дополнительные задания;
- отслеживать прогресс обучения.
Центральный компонент системы — AI-наставник, который анализирует ответы пользователя и предлагает дальнейшие направления обучения.
1.1. Основной пользовательский сценарий
1. Пользователь изучает новую тему Python.
2. Создаёт карточку с вопросом, ответом и дополнительными материалами.
3. Приложение проверяет качество карточки.
4. Пользователь запускает повторение.
5. Отвечает на вопрос самостоятельно.
6. AI анализирует ответ и предоставляет обратную связь.
7. Пользователь видит оценку и выявленные пробелы.
8. Backend рассчитывает следующее повторение.
9. AI при необходимости предлагает дополнительные карточки и тесты.
10. Пользователь подтверждает или отклоняет предложения.
11. Статистика обновляется.

3. Архитектурные принципы
Система строится на модульной архитектуре с разделением ответственности.

Основные принципы:

1. Separation of Concerns

Разделение HTTP-слоя, бизнес-логики, доступа к данным и AI-интеграций.

2. Provider Independence

Бизнес-логика не должна зависеть от конкретной LLM.

3. AI as Assistant

AI предлагает решения, но не изменяет пользовательские данные самостоятельно.

4. Deterministic Business Logic

Расписание повторений, сохранение оценок и расчёт статистики выполняются Backend, а не LLM.

5. Offline First

Основные функции приложения доступны без интернета и внешних AI-сервисов.

6. Extensibility

Возможность добавлять новых AI-провайдеров и новые алгоритмы обучения без существенного изменения существующих модулей.

4.4. Review Engine — интервальное повторение
Модуль отвечает за организацию процесса обучения.
Алгоритм
Для первой версии используется SM-2.

Оценки:
Значение	Название	Интерпретация
0–2	Again	Не помню
3	Hard	Трудно
4	Good	Хорошо
5	Easy	Легко


Внутри Backend сохраняются:
- repetitions;
- interval_days;
- ease_factor;
- next_review_at;
- last_reviewed_at.
Логика повторения
1. Получение карточек, срок повторения которых наступил.
2. Отображение вопроса.
3. Получение ответа пользователя.
4. Отображение эталонного ответа.
5. AI-анализ ответа, если включён соответствующий режим.
6. Получение пользовательской оценки.
7. Расчёт следующего интервала.
8. Сохранение результата и истории.
Два режима обучения
Обычный режим

Пользователь самостоятельно оценивает, насколько хорошо вспомнил материал.

AI-режим

AI анализирует ответ, а пользователь дополнительно получает оценку полноты и рекомендации.

Важно: AI-оценка и SM-2 — разные механизмы. AI не должен напрямую изменять коэффициенты SM-2.

Для первой версии SM-2 получает оценку пользователя. В дальнейшем можно добавить настраиваемый режим, в котором AI предлагает оценку, а пользователь подтверждает её.
Дополнительные функции
- Повторение всех просроченных карточек.
- Повторение конкретной темы.
- Повторение сложных карточек.
- Ручное повторение.
- Ограничение количества новых карточек в день.
- Просмотр истории повторений.
5. AI Mentor — интеллектуальный наставник
Это основной отличительный модуль проекта.

AI Mentor должен помогать пользователю не только запоминать определения, но и понимать Python.

На первом этапе это единый AI-сервис с четырьмя независимыми сценариями работы.
5.1. Answer Evaluator — проверка ответов
Назначение
Проверять ответы пользователя на учебные вопросы.
Входные данные
- текст вопроса;
- эталонный ответ;
- дополнительное пояснение;
- пример кода, если есть;
- ответ пользователя;
- сложность карточки.
Результат анализа
AI должен определить:
1. Правильно ли пользователь понял концепцию.
2. Какие ключевые понятия раскрыты.
3. Какие важные элементы пропущены.
4. Есть ли фактические ошибки.
5. Есть ли логические противоречия.
6. Насколько ответ полный.
7. Что рекомендуется повторить.
Формат оценки
Показатель	Значение
correctness	Правильность
completeness	Полнота
score	Оценка от 0 до 100
missing_concepts	Пропущенные понятия
mistakes	Ошибки
feedback	Обратная связь
recommendation	Рекомендации


Пример:

Пользователь отвечает на вопрос о декораторах.

AI обнаруживает, что определение правильное, но отсутствует понимание передачи аргументов и сохранения метаданных функции.

Результат:
- правильность: высокая;
- полнота: 75%;
- ошибки: отсутствуют;
- рекомендации: повторить *args, **kwargs и functools.wraps.
Важные ограничения
- Не требовать дословного совпадения с эталонным ответом.
- Принимать альтернативные корректные формулировки.
- Не считать отсутствие необязательной информации ошибкой.
- Разделять фактические ошибки и неполноту.
- Не придумывать ошибки, если ответ правильный.
- При недостаточном контексте возвращать статус needs_review.
Оценка AI не является абсолютной истиной. Пользователь должен иметь возможность оспорить её и самостоятельно выбрать итоговую оценку повторения.
5.2. Card Analyzer — анализ качества карточек
Назначение
Проверять качество создаваемых пользователем карточек.
Проверяемые параметры
Параметр	Что проверяет
Question clarity	Понятность вопроса
Answer completeness	Полнота ответа
Accuracy	Фактическая корректность
Specificity	Конкретность вопроса
Learning value	Полезность для обучения


Возможные рекомендации
- Вопрос слишком общий.
- Ответ недостаточно раскрывает тему.
- В ответе отсутствует важное свойство.
- Пример кода не соответствует описанию.
- Вопрос содержит несколько независимых вопросов.
- Карточка дублирует существующую.
Результат
AI формирует:
- список проблем;
- объяснение каждой проблемы;
- предложенную редакцию вопроса;
- предложенную редакцию ответа;
- рекомендации по дополнительным примерам.
Важно: оригинальная карточка не изменяется автоматически.

Пользователь может принять предложение целиком, принять отдельные изменения или отклонить его.
5.3. Card Generator — генерация новых карточек
Назначение
Автоматически создавать дополнительные учебные карточки.
Источники генерации
- существующая тема;
- выбранная категория;
- существующие карточки;
- выявленные пробелы в знаниях;
- пользовательский текст или конспект;
- конкретный запрос пользователя.
Примеры генерации
Для темы «Декораторы»:
- Теоретические вопросы.
- Практические задания.
- Вопросы на сравнение.
- Вопросы на поиск ошибок.
- Задания с написанием кода.
Требования
AI должен:
1. Проанализировать выбранную тему.
2. Определить имеющееся покрытие материала.
3. Найти недостаточно раскрытые области.
4. Сформировать новые карточки.
5. Проверить корректность ответов.
6. Проверить возможные дубликаты.
7. Передать карточки на подтверждение пользователю.
Новые карточки сохраняются в отдельном разделе предложений.

Автоматическое добавление в основную базу запрещено.

- Предложение дополнительных карточек.
- Формирование тематических тестов.

Пример:

Пользователь регулярно путает classmethod и staticmethod.

Агент:
1. Выявляет повторяющуюся проблему.
2. Формирует рекомендацию.

Адаптивный наставник не должен самостоятельно менять расписание SM-2.
6. AI Provider Manager — управление AI-провайдерами
Модуль отвечает за подключение и переключение моделей.
6.1. Основной провайдер
Ollama.

Первоначальная модель — Qwen 3 4B в квантованном формате.

С учётом оборудования пользователя:
- 16 GB RAM;
- RTX 2050 4 GB VRAM;
- AMD Ryzen 7 7435HS.
Необходимо протестировать фактическую скорость и потребление памяти. При необходимости использовать более компактную модель.

Основные требования:
- локальный запуск;
- отсутствие оплаты за токены;
- работа без VPN;
- отсутствие обязательного подключения к интернету после загрузки модели.
Оговорка: локальная модель не означает буквально бесконечную производительность. Ограничениями будут оперативная память, видеопамять и вычислительные ресурсы.
6.2. Дополнительные провайдеры
Провайдер	Назначение

Сервисам AI не нужно знать, какая конкретно модель выполняет запрос.
6.4. Управление токенами
Система должна учитывать:
- входящие токены;
- исходящие токены;
- общее потребление;
- количество запросов;
- потребление по типам задач;
- потребление по провайдерам;
- ошибки и ограничения квот.
Для локальной модели токены также можно учитывать, хотя они не имеют денежной стоимости.
Ограничения
- Максимальный размер контекста.
- Максимальный размер ответа.
- Лимит облачных запросов в день.
- Возможность полностью отключить облачные модели.
- Возможность использовать только локальную модель.
Переключение провайдера
При недоступности облачного API:
1. Проверяется наличие локальной модели.
2. Запрос направляется в Ollama.
3. Результат возвращается в стандартном формате.
4. Ошибка облачного провайдера сохраняется в журнале.
При исчерпании бесплатной квоты система не должна пытаться автоматически перейти на платный тариф.

В MVP приложение локальное и однопользовательское.

16. Дополнительные архитектурные решения
Есть несколько моментов, которые предлагаю зафиксировать заранее.
16.1. Не использовать сложную агентную архитектуру на старте
Для MVP достаточно одного AI-сервиса с несколькими специализированными сценариями.

Не нужны LangChain, LangGraph и многоуровневая система автономных агентов.

При необходимости их можно изучить и добавить позже.
16.2. AI не должен быть источником истины
Эталонный материал хранится в базе.

AI анализирует ответ относительно эталона и общепринятых знаний Python, но не может произвольно менять правильные ответы.

Для спорных случаев предусматривается ручная проверка.
16.3. Проверка качества AI
Необходимо предусмотреть контрольный набор вопросов с заранее подготовленными ответами.

Это позволит сравнивать модели и выбирать наиболее подходящую.

Например, Qwen 3 4B может хорошо справляться с короткими определениями, но хуже оценивать сложные объяснения с несколькими взаимосвязанными концепциями.

Поэтому выбор модели должен основываться на результатах тестирования, а не только на количестве параметров.
16.4. Отдельно учитывать токены и деньги
Это разные показатели.

Для локальных моделей:
- входящие токены;
- исходящие токены;
- общее количество токенов;
- денежная стоимость — 0.
Для облачных:
- входящие токены;
- исходящие токены;
- использованная бесплатная квота, если провайдер предоставляет такие данные;
- стоимость — 0 в пределах бесплатного тарифа.
Если провайдер не возвращает точную статистику токенов, приложение должно использовать оценку и помечать её как приблизительную.
