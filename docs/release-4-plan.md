# План работ Release 4: Adaptive Learning

- Статус: черновик для согласования
- Дата: 2026-11-12
- Результат релиза: приложение объяснимо выявляет слабые темы, предлагает
  следующие учебные действия и позволяет проходить тематические тесты

## Правила выполнения

Этапы выполняются последовательно. Тесты создаются вместе с функциональностью.
После каждого этапа:

1. фиксируется проверяемый результат;
2. запускаются относящиеся к нему проверки;
3. пользовательский сценарий проверяется вручную;
4. создаётся отдельный коммит;
5. только затем начинается следующий этап.

Адаптивное ядро работает без AI. Ни рекомендация, ни тест не меняют карточки или
SM-2 без существующего явного пользовательского действия.

## 4.0. Архитектура и границы релиза

**Результат:** [ADR-005](adr/ADR-005-adaptive-learning-architecture.md) и этот
план.

- разделить детерминированные учебные сигналы и AI-объяснения;
- определить состояние недостаточных данных;
- зафиксировать жизненный цикл рекомендаций;
- отделить тематические тесты от Review Engine;
- сохранить подтверждение карточек и пользовательскую оценку SM-2;
- вынести импорт/экспорт и облачные провайдеры в независимые этапы.

**Проверки:** ADR не противоречит ADR-001 и ADR-004, `spec.md` и существующим
транзакционным границам.

**Предлагаемый коммит:** `docs: define release 4 adaptive architecture`

## 4.1. Контракт учебных сигналов и слабых тем

**Результат:** [ADR-006](adr/ADR-006-learning-signals.md) и Backend API,
возвращающий объяснимую сводку по темам без вызова AI.

- зафиксировать окно анализа, минимальный объём истории и контрольные примеры;
- определить сигналы из `review_logs`, карточек и `answer_evaluations`;
- различать `insufficient_data`, `stable` и `needs_attention`;
- возвращать причины статуса и объём исходных данных;
- добавить фильтры по категории, статусу и периоду;
- не сохранять производные показатели в универсальную таблицу заранее;
- согласовать OpenAPI-контракт до реализации endpoint.

**Тесты вместе с кодом:** новая тема, недостаток истории, частые `Again`,
устойчивая тема, просроченные карточки, наличие и отсутствие AI-оценок,
архивные карточки, границы периода и часового пояса.

**Проверки:** Backend check, OpenAPI check, PostgreSQL query smoke.

**Предлагаемый коммит:** `feat: add adaptive learning signals api`

## 4.2. Интерфейс адаптивной аналитики

**Результат:** пользователь видит слабые темы и понимает причину вывода.

- добавить раздел «План обучения»;
- показать состояния «недостаточно данных», «стабильно» и «нужно внимание»;
- вывести числовые сигналы и понятные русские объяснения;
- добавить фильтры и переход к карточкам или повторению выбранной темы;
- не использовать цвет как единственный способ обозначения статуса;
- обеспечить loading, empty, error и unavailable states.

**Тесты вместе с кодом:** все статусы, фильтры, пустая история, переходы к
повторению, доступность с клавиатуры и production routing.

**Проверки:** Frontend check, production build и ручная проверка на истории
реальных повторений.

**Предлагаемый коммит:** `feat: add adaptive learning dashboard`

## 4.3. Рекомендации и повторяющиеся пробелы

**Результат:** слабые сигналы превращаются в сохранённые предложения дальнейших
действий, которые пользователь может выполнить или отклонить.

- определить сущность рекомендации и статусы `pending/completed/dismissed`;
- сохранять источник, причины, входной снимок и версию правил;
- агрегировать повторяющиеся пропуски только в пределах темы;
- не считать похожие свободные формулировки одинаковыми без явного правила;
- добавить необязательный типизированный сценарий Adaptive Tutor;
- разрешить детерминированные рекомендации при отключённом AI;
- реализовать list/filter и явные complete/dismiss команды.

**Тесты вместе с кодом:** рекомендации без AI, AI-объяснение, недостаток данных,
повторяющиеся пробелы, идемпотентность, provider errors, жизненный цикл и
отсутствие изменений SM-2.

**Проверки:** миграции upgrade/downgrade/check, Backend check, OpenAPI check и
fake-provider smoke.

**Предлагаемый коммит:** `feat: add adaptive learning recommendations`

## 4.4. Действия по рекомендации

**Результат:** рекомендацию можно безопасно превратить в конкретное учебное
действие.

- показать список и историю рекомендаций;
- открыть повторение рекомендованной темы;
- передать тему или выявленный пробел в существующий Card Generator;
- сохранить новые карточки только как `pending` suggestions;
- отметить рекомендацию выполненной или отклонённой отдельной командой;
- не завершать рекомендацию автоматически при сетевой ошибке.

**Тесты вместе с кодом:** repeat action, generate action, accept/reject карточки,
повторная команда, недоступный Ollama и ручное завершение.

**Проверки:** Backend/Frontend checks, production build и ручная цепочка
weak topic → recommendation → pending card → accept.

**Предлагаемый коммит:** `feat: connect recommendations to learning actions`

## 4.5. Тематические тесты Backend

**Результат:** по выбранной или слабой теме можно создать и пройти отдельный
тест на основе подтверждённых карточек.

- определить test session, неизменяемые снимки вопросов и ответы пользователя;
- в первой версии выбирать вопросы из существующих неархивных карточек;
- не раскрывать эталон до подтверждения ответа;
- рассчитывать результат теста отдельно от SM-2;
- сохранять прогресс и итог с идемпотентным завершением;
- предусмотреть источник `topic` или `recommendation`;
- отложить AI-сгенерированные тестовые вопросы до проверки базового сценария.

**Тесты вместе с кодом:** создание, недостаток карточек, порядок вопросов,
снимки после редактирования карточки, частичное прохождение, завершение,
идемпотентность и неизменность SM-2.

**Проверки:** миграции, Backend check, OpenAPI check и API smoke.

**Предлагаемый коммит:** `feat: add thematic practice tests api`

## 4.6. Интерфейс тематических тестов

**Результат:** тематический тест полностью проходится в браузере.

- запускать тест из темы или рекомендации;
- показывать прогресс без преждевременного раскрытия ответа;
- сохранять ответ и показывать эталон после подтверждения;
- показывать итог по тесту и темы для повторения;
- поддержать перезагрузку страницы и продолжение незавершённой сессии;
- обеспечить клавиатурную навигацию и русские состояния ошибок.

**Тесты вместе с кодом:** полный сценарий, продолжение сессии, пустая тема,
ошибка сохранения, итог и отсутствие вызовов Review Engine.

**Проверки:** Frontend check, production build и ручной тематический тест.

**Предлагаемый коммит:** `feat: add thematic practice test interface`

## 4.7. Импорт, экспорт и резервная копия

**Результат:** знания и история переносимы между установками приложения.

- определить версионированный JSON backup format;
- экспортировать категории, темы, теги, карточки и историю повторений;
- не экспортировать секреты и локальную конфигурацию;
- валидировать весь импорт до записи и показывать preview;
- определить стратегию UUID и дубликатов;
- выполнять восстановление транзакционно без AI-вызовов;
- добавить CSV preview/import для карточек отдельным подэтапом.

**Тесты вместе с кодом:** round trip, несовместимая версия, битый файл,
дубликаты, rollback, большие наборы, отсутствие секретов и восстановление SM-2.

**Проверки:** Backend/Frontend checks и восстановление в чистую временную БД.

**Предлагаемый коммит:** `feat: add versioned knowledge backup`

## 4.8. Необязательный облачный провайдер

**Результат:** после отдельного согласования один облачный провайдер может быть
явно включён без изменения AI-сценариев.

- перед выбором заново проверить официальные API, квоты, регионы и правила
  обработки данных;
- выбрать только один первый провайдер и оформить отдельный ADR;
- хранить API-ключ только в Backend environment;
- добавить явный `cloud_ai_enabled` и выбор провайдера;
- не выполнять скрытый fallback с Ollama в облако;
- учитывать provider/model, ошибки, токены и приблизительность метрик;
- не блокировать готовность адаптивного ядра отсутствием облачного ключа.

**Тесты вместе с кодом:** disabled, missing key, readiness, structured output,
timeout, quota/rate limit, безопасные ошибки, локальный fallback и отсутствие
секрета в API/logs.

**Проверки:** provider unit/contract tests и только явный opt-in live smoke.

**Предлагаемый коммит:** `feat: add optional cloud ai provider`

## Критерии готовности адаптивного ядра

- слабая тема определяется прозрачными сигналами, а не свободным выводом AI;
- отсутствие истории отображается как недостаток данных;
- пользователь видит причины и объём данных для рекомендации;
- рекомендации доступны без AI и требуют явного действия;
- дополнительные карточки остаются предложениями до accept;
- тематические тесты не меняют SM-2;
- AI и облачные провайдеры остаются необязательными;
- backup позволяет восстановить знания и историю без повторного запуска AI.
