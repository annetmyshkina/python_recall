# ADR-003: Архитектура Frontend

- Статус: принято
- Дата: 2026-11-07
- Область: Release 2 Frontend

## Контекст

Release 1 предоставляет самостоятельный FastAPI REST API. В Release 2 нужен
браузерный интерфейс для управления базой знаний, повторения карточек и просмотра
статистики. Frontend должен оставаться отдельным приложением, не переносить в
браузер бизнес-правила SM-2 и не зависеть от AI-функций, которые появятся только
в Release 3.

Нужно определить структуру приложения, границы состояния, способ работы с API,
тестовую стратегию и правила локального запуска до начала реализации экранов.

## Решение

### Приложение и инструменты

Frontend реализуется как одностраничное приложение на React 19 и TypeScript со
строгой проверкой типов. Vite отвечает за локальную разработку и production
build. Зависимости Frontend устанавливаются через npm и фиксируются в
`package-lock.json`; Python-зависимости по-прежнему управляются через uv.

Используем стек, определённый спецификацией:

| Задача | Решение |
|---|---|
| Маршрутизация | React Router |
| Серверное состояние | TanStack Query |
| Формы | React Hook Form |
| Валидация форм | Zod |
| Стили | Tailwind CSS и небольшое число дизайн-токенов |
| Unit/component tests | Vitest и React Testing Library |
| Имитация HTTP в тестах | MSW |
| Типы HTTP-контракта | генерация из `docs/openapi.yaml` |

Redux или другой глобальный store в Release 2 не добавляется. Серверные данные
принадлежат TanStack Query, фильтры и выбранные сущности по возможности отражаются
в URL, а краткоживущее состояние интерфейса остаётся внутри компонентов.

### Структура исходного кода

```text
frontend/src/
├── app/          # router, providers и корневой layout
├── components/   # переиспользуемые UI- и layout-компоненты
├── features/     # dashboard, knowledge-base, reviews, statistics
├── hooks/        # общие React hooks
├── lib/          # API client, query client, форматирование
├── styles/       # глобальные стили и дизайн-токены
└── types/        # общие и сгенерированные API-типы
```

Каждая feature-папка содержит относящиеся к сценарию API-функции, query hooks,
компоненты, схемы форм и тесты. Общий компонент переносится в `components` только
после появления реального повторного использования.

### Маршруты Release 2

| Путь | Назначение |
|---|---|
| `/` | Dashboard и быстрый старт повторения |
| `/cards` | Список, поиск и фильтрация карточек |
| `/cards/new` | Создание карточки |
| `/cards/:cardId/edit` | Редактирование карточки |
| `/topics` | Категории, темы и карточки выбранной темы |
| `/review` | Очередь и прохождение повторения |
| `/statistics` | Общая, тематическая и временная статистика |

Неизвестный маршрут показывает контролируемую страницу `404`. Ошибка отдельного
экрана не должна разрушать весь layout приложения.

### Работа с REST API

Frontend обращается только к относительному пути `/api/v1`. В режиме разработки
Vite проксирует его в FastAPI. В контейнерном production-режиме тот же путь
проксирует web server Frontend. Благодаря одному origin приложению не нужна
отдельная CORS-конфигурация.

`docs/openapi.yaml` остаётся источником истины внешнего контракта. Из него
генерируется и коммитится файл типов, а небольшой общий API client отвечает за:

- JSON и пустые ответы `204`;
- query-параметры и `AbortSignal`;
- Problem Details (`application/problem+json`);
- единый тип ошибки для экранов и форм;
- заголовок `Idempotency-Key` при подтверждении повторения.

Автоматически сгенерированный полноценный SDK пока не используется: небольшой
явный слой запросов проще читать и отлаживать, а генерация типов защищает границу
контракта от расхождений.

Backend остаётся единственным владельцем бизнес-правил. Frontend не вычисляет
SM-2, не назначает даты следующего повторения и не пересчитывает статистику. Он
показывает данные и новое состояние, полученные от API.

### Состояния интерфейса

Каждый экран явно обрабатывает четыре состояния: загрузка, данные, пустой
результат и ошибка. После мутаций инвалидируются только связанные query keys.
Оптимистические изменения допускаются лишь для обратимых действий, если они не
могут скрыть серверный конфликт. Создание, удаление и подтверждение повторения
сначала подтверждаются Backend.

Фильтры списка карточек и пагинация хранятся в query string, чтобы обновление
страницы и кнопка Back не теряли контекст.

### Безопасность отображения

Текст карточек считается недоверенным. Markdown отображается без исполнения
встроенного HTML, а `code_example` — только как текст. Frontend не хранит и не
получает AI-ключи или другие секреты.

### Доступность и адаптивность

Интерфейс проектируется сначала для небольшого экрана, затем расширяется для
desktop. Интерактивные элементы доступны с клавиатуры, формы имеют связанные
labels, ошибки не передаются одним цветом, диалоги управляют фокусом, а основные
экраны используют семантические заголовки и landmark-области.

### Тестовая стратегия

Тесты создаются вместе с функциональностью, а не отдельным завершающим этапом:

- чистые функции проверяются unit-тестами;
- формы и пользовательские сценарии — React Testing Library;
- сетевые ответы и ошибки — MSW на уровне публичного HTTP-контракта;
- на каждом этапе выполняются typecheck, lint, tests и production build;
- итоговый этап Release 2 повторяет все проверки и smoke-сценарий с настоящим
  Backend и PostgreSQL.

Тесты проверяют наблюдаемое поведение пользователя и не привязываются к
внутренней структуре компонентов.

### Граница Release 2 и AI

Release 2 не имитирует отсутствующий AI API и не создаёт фиктивные рекомендации.
Обычный SM-2 сценарий полностью работает без AI. AI-анализ ответа, рекомендации,
предложения карточек и страница наставника добавляются вместе с контрактами
Release 3. Если интерфейс упоминает будущую функцию, она явно помечается как
недоступная, а не показывает вымышленные данные.

## Последствия

Положительные:

- контракт Frontend с Backend проверяется автоматически;
- серверные данные и локальное UI-состояние не смешиваются;
- страницы можно реализовывать и коммитить по одной функциональной области;
- обычное повторение не зависит от AI;
- одинаковый `/api/v1` используется локально и в контейнерах;
- тесты появляются одновременно с пользовательскими сценариями.

Ограничения:

- npm становится вторым менеджером зависимостей рядом с uv;
- сгенерированные API-типы нужно обновлять при изменении OpenAPI;
- без отдельного глобального store сложное клиентское состояние в будущем может
  потребовать нового решения;
- полноценные browser end-to-end тесты не являются основным слоем Release 2 и
  могут быть добавлены после стабилизации ключевых сценариев.

## Отклонённые варианты

- Серверный рендеринг — не даёт заметной пользы локальному однопользовательскому
  приложению и усложняет deployment.
- Хранить API-данные в Redux — дублирует кэш и жизненный цикл TanStack Query.
- Писать типы REST вручную — повышает риск расхождения с OpenAPI.
- Использовать абсолютный URL Backend в браузере — создаёт лишнюю CORS- и
  environment-конфигурацию.
- Реализовать заглушки AI как будто это готовые данные — маскирует границу между
  Release 2 и Release 3.
