# ADR-001: Алгоритм интервального повторения

- Статус: принято
- Дата: 2026-11-06
- Область: Review Engine

## Контекст

Python Recall должен рассчитывать расписание повторений детерминированно и
работать без AI. Спецификация выбирает SM-2, но не фиксирует точное соответствие
кнопок оценкам качества, порядок обновления состояния и границы ответственности
между ответом пользователя, AI-анализом и итогом повторения.

Без этих правил разные клиенты или реализации Backend могут рассчитывать разные
интервалы для одной и той же истории карточки.

## Решение 1: вариант SM-2

Используем классический SM-2 с целочисленной оценкой качества `q` от 0 до 5.
Коэффициент лёгкости обновляется после каждого подтверждённого повторения:

```text
EF' = max(1.3, EF + 0.1 - (5 - q) * (0.08 + (5 - q) * 0.02))
```

Начальное состояние новой карточки:

| Поле | Значение |
|---|---:|
| `repetitions` | `0` |
| `interval_days` | `0` |
| `ease_factor` | `2.5` |
| `last_reviewed_at` | `null` |

Новая неархивная карточка доступна для изучения сразу. Конкретное представление
этого правила в поле `next_review_at` и правила календарных границ будут
зафиксированы вместе с моделью данных и правилами работы с датами.

### Отображение пользовательских оценок

| Кнопка | `q` | Значение |
|---|---:|---|
| `Again` | `1` | Не вспомнил или ответил неправильно |
| `Hard` | `3` | Вспомнил с трудом |
| `Good` | `4` | Ответил правильно |
| `Easy` | `5` | Ответил легко |

Ядро алгоритма сохраняет совместимость со значениями `q = 0..5`. Штатный
интерфейс первой версии формирует только четыре значения из таблицы выше.
Неизвестная пользовательская оценка или `q` вне диапазона `0..5` отклоняются до
изменения состояния карточки.

### Расчёт следующего состояния

Пусть до повторения состояние карточки равно `(R, I, EF)`, где:

- `R` — число последовательных успешных повторений;
- `I` — текущий интервал в днях;
- `EF` — текущий коэффициент лёгкости.

Следующее состояние рассчитывается так:

1. Если `q < 3`, установить `R' = 0` и `I' = 1`.
2. Если `q >= 3` и `R = 0`, установить `R' = 1` и `I' = 1`.
3. Если `q >= 3` и `R = 1`, установить `R' = 2` и `I' = 6`.
4. Если `q >= 3` и `R >= 2`, установить `R' = R + 1` и
   `I' = max(1, round_half_up(I * EF))`.
5. Для любого допустимого `q` рассчитать `EF'` по формуле выше и ограничить его
   снизу значением `1.3`.

При расчёте шага 4 используется `EF` до текущего повторения. Значение `EF'`
сохраняется для последующих повторений. Для округления применяется правило
`round half up`, а не зависящее от языка банковское округление.

Алгоритм представляет собой чистую функцию: прежнее состояние и `q` полностью
определяют новое состояние. Он возвращает интервал в календарных днях, но не
работает с системными часами. `last_reviewed_at` и `next_review_at` рассчитывает
сервис повторений согласно отдельно зафиксированным правилам UTC и часового
пояса.

### Контрольные примеры

| Исходное состояние `(R, I, EF)` | Оценка | Новое состояние `(R', I', EF')` |
|---|---|---|
| `(0, 0, 2.50)` | `Good` | `(1, 1, 2.50)` |
| `(1, 1, 2.50)` | `Good` | `(2, 6, 2.50)` |
| `(2, 6, 2.50)` | `Good` | `(3, 15, 2.50)` |
| `(3, 15, 2.50)` | `Hard` | `(4, 38, 2.36)` |
| `(3, 15, 2.50)` | `Again` | `(0, 1, 1.96)` |
| `(2, 6, 1.30)` | `Again` | `(0, 1, 1.30)` |

Числа `EF` при хранении и сравнении должны рассчитываться предсказуемо, без
накопления двоичных ошибок, влияющих на округление интервала. Конкретный тип
поля БД будет выбран на этапе проектирования сущностей.

## Решение 2: разделение ответа, AI-анализа и результата повторения

В доменной модели это три разные операции:

1. **Ответ пользователя.** Пользователь может написать ответ и продолжить без
   AI. Наличие текста ответа не даёт системе права менять расписание.
2. **AI-анализ.** Необязательная операция над ответом и эталонным материалом.
   Она может вернуть оценку качества и рекомендацию, но не изменяет состояние
   SM-2.
3. **Результат повторения.** Пользователь самостоятельно подтверждает одну из
   оценок `Again`, `Hard`, `Good`, `Easy`. Только эта операция запускает SM-2.

Недоступность, таймаут или некорректный ответ AI не блокируют сохранение
пользовательской оценки. Предложенная AI оценка в будущих версиях также должна
быть явно подтверждена пользователем.

### Транзакционная граница

В одной транзакции сохраняются:

- подтверждённая пользовательская оценка;
- прежнее и новое состояние SM-2;
- `last_reviewed_at` и `next_review_at`;
- одна запись истории повторения (`review_log`).

При ошибке любого из этих действий транзакция полностью откатывается. Сохранение
текста ответа и AI-анализа может происходить отдельно и не включается в эту
транзакционную границу.

### Идемпотентность результата повторения

Команда подтверждения оценки обязана содержать ключ идемпотентности, созданный
клиентом для конкретного результата повторения.

- Первый запрос с новым ключом выполняет расчёт и фиксирует результат.
- Повторный запрос с тем же ключом и тем же содержимым возвращает ранее
  сохранённый результат и не создаёт новый `review_log`.
- Тот же ключ с другим содержимым считается конфликтом и не меняет данные.
- Проверка ключа и запись результата входят в одну транзакцию.
- В однопользовательском MVP ключ уникален в пределах всех результатов
  повторений.

Формат передачи ключа, HTTP-код конфликта и точное место его хранения будут
зафиксированы в модели данных и REST API. Независимо от физической реализации
история должна позволять однозначно вернуть исходный результат повторного
запроса.

## Инварианты

- AI никогда напрямую не изменяет `repetitions`, `interval_days`, `ease_factor`
  или даты повторения.
- Без подтверждённой пользовательской оценки состояние SM-2 не изменяется.
- Одно подтверждение создаёт не более одной записи истории.
- Архивная карточка не попадает в автоматическую очередь повторения.
- Расчёт SM-2 не зависит от провайдера AI, сети, базы данных или системных часов.
- Для каждого изменения состояния в истории сохраняются старые и новые значения.

## Проверки при реализации

Unit-тесты алгоритма создаются одновременно с Review Engine и должны покрывать:

- первые два успешных повторения с интервалами 1 и 6 дней;
- умножение последующих интервалов и `round half up`;
- все значения `q` от 0 до 5;
- сброс `repetitions` и интервала при `q < 3`;
- нижнюю границу `EF = 1.3`;
- неизменяемость исходного состояния;
- отклонение недопустимых оценок;
- контрольные примеры из этого ADR.

Интеграционные тесты сервиса должны доказать атомарность транзакции и отсутствие
дублирования при повторной отправке ключа идемпотентности.

## Последствия

Положительные:

- расписание остаётся детерминированным и доступным без AI;
- поведение можно полностью проверить unit-тестами;
- повтор сетевого запроса безопасен;
- AI можно развивать независимо от Review Engine.

Ограничения первой версии:

- нет внутридневных learning steps;
- нет FSRS, leech detection, bury/suspend и автоматической корректировки оценки;
- одна кнопка `Again` представляет все неуспешные оценки интерфейса;
- текст ответа и AI-анализ не являются частью атомарной фиксации SM-2.

## Отклонённые варианты

- Разрешить AI самостоятельно выбирать итоговую оценку и изменять SM-2 — нарушает
  принцип подтверждения пользователем и делает обучение зависимым от AI.
- Связать сохранение оценки с успешным AI-анализом — ломает offline-first режим.
- Использовать отдельную формулу для каждой UI-кнопки — теряется совместимость с
  классическим SM-2.
- Добавить FSRS на первом релизе — увеличивает объём реализации до накопления
  достаточной истории для его настройки.
