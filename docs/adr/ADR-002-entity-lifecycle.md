# ADR-002: Жизненный цикл, удаление и архивация сущностей

- Статус: принято
- Дата: 2026-11-06
- Область: Knowledge Base и Review Engine

## Контекст

Спецификация требует удаление категорий, тем и карточек, а для карточек также
архивацию. Простое каскадное удаление категории может незаметно уничтожить
карточки и историю обучения. Полный запрет физического удаления, напротив,
оставляет в базе ошибочно созданные пустые сущности.

Нужно сохранить историю и при этом разрешить безопасное исправление данных.

## Решение

Используем физическое удаление только там, где оно не уничтожает учебную
историю. Для изученных карточек используем обратимую архивацию.

### Матрица операций

| Сущность | Физическое удаление | Архивация | Правило |
|---|---|---|---|
| Category | Да | Нет | Только если нет тем |
| Topic | Да | Нет | Только если нет карточек, включая архивные |
| Card | Условно | Да | Удаляется только без попыток и повторений |
| Tag | Да | Нет | Связи CardTag удаляются каскадно |
| CardTag | Да | Нет | Техническая связь удаляется вместе с Card или Tag |
| AnswerAttempt | Нет через публичный API | Нет | Неизменяемая история ответа |
| ReviewLog | Нет через публичный API | Нет | Неизменяемый факт повторения |

Наличие зависимостей проверяется сервисом и гарантируется ограничениями FK.
Запрещённое удаление не выполняется частично и возвращает доменный конфликт;
точный HTTP-ответ будет зафиксирован в `api.md`.

### Category

Категория удаляется только после явного удаления или переноса всех её тем.
Каскадное удаление дерева Category -> Topic -> Card запрещено.

### Topic

Тема удаляется только после явного удаления или переноса всех карточек. Архивные
карточки также блокируют удаление темы, потому что остаются частью базы знаний.

### Card

Карточка без `AnswerAttempt` и `ReviewLog` может быть физически удалена. Её связи
с тегами удаляются в той же транзакции.

Если существует хотя бы одна попытка или запись повторения, физическое удаление
запрещено. Пользователь может архивировать карточку. В Release 1 нет `force
delete`, каскадного удаления истории или очистки истории отдельной командой.

Будущие AI-данные не должны ослаблять это правило. Их ссылки проектируются в
Release 3 после определения конкретных AI-сценариев.

### Tag

Удаление тега удаляет только строки `CardTag`. Карточки и их история сохраняются.
Тег не архивируется, поскольку не участвует в очереди обучения и может быть
безопасно создан заново.

### Исторические сущности

`AnswerAttempt` и `ReviewLog` после создания не редактируются и не удаляются
через публичный API. Исправление технических ошибок выполняется отдельной
административной процедурой вне MVP, а не обычным CRUD.

## Семантика архивации Card

Архивация меняет только `is_archived` и `updated_at`.

Архивная карточка:

- исключается из очередей новых и просроченных карточек;
- не может получить новое подтверждённое повторение;
- не учитывается в показателях текущего активного набора;
- остаётся доступной через явный фильтр и прямое получение;
- сохраняет тему, теги, SM-2 state, попытки и историю повторений;
- продолжает учитываться в исторической статистике за прошлые периоды.

Разархивация не сбрасывает SM-2. Если сохранённый `next_review_at` уже наступил,
карточка снова становится доступной для повторения сразу. Новая карточка после
разархивации остаётся новой.

Архивация не распространяется автоматически на соседние карточки, тему или
категорию. Массовая архивация, если появится, должна быть явной операцией над
выбранными карточками.

## Изменение и перемещение Card

Редактирование вопроса, ответа, пояснения, примера, сложности или тегов не
сбрасывает расписание и не изменяет историю. Перемещение в другую тему также
сохраняет историю и SM-2 state.

Автоматический сброс отклонён, потому что Backend не может надёжно определить,
является ли правка исправлением опечатки или полной заменой изучаемого понятия.
Если позднее потребуется сброс прогресса, это будет отдельная подтверждаемая
команда со своей записью аудита.

## Согласованность при конкурентных действиях

Даже в однопользовательском приложении несколько вкладок могут отправить запросы
одновременно. Поэтому:

- возможность удаления проверяется внутри транзакции;
- FK остаются окончательной защитой от удаления родителя;
- подтверждение повторения повторно проверяет, что Card не архивирована;
- изменение состояния Card и создание ReviewLog выполняются атомарно;
- ключ идемпотентности защищает от дублирования одного результата повторения.

## Последствия

Положительные:

- случайное удаление категории не уничтожает всю базу знаний;
- история и статистика остаются воспроизводимыми;
- ошибочно созданные пустые сущности можно удалить без soft-delete инфраструктуры;
- архивация карточки полностью обратима;
- правила можно обеспечить одновременно сервисами и FK.

Ограничения:

- для удаления непустой категории или темы нужны явные промежуточные действия;
- изученную карточку нельзя физически удалить через обычный API;
- категории и темы пока нельзя скрыть архивацией;
- отдельная процедура полного удаления персональных данных не входит в MVP.

## Отклонённые варианты

- Каскадно удалять всё дерево категории — слишком высокий риск потери данных.
- Использовать soft delete для каждой таблицы — усложняет все запросы без пользы
  для тегов и пустых организационных сущностей.
- Запретить любое физическое удаление — оставляет мусор после ошибочного создания.
- Сбрасывать SM-2 после любого редактирования — не различает косметические и
  смысловые изменения.
- Создать AI-таблицы и FK заранее — фиксирует модель до реализации AI-сценариев.
