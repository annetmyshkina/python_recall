# ADR-004: Архитектура AI-модуля

- Статус: принято для Release 3
- Дата: 2026-11-09
- Область: AI Mentor и интеграция с провайдерами

## Контекст

Release 1 и Release 2 не зависят от AI: база знаний, повторения, SM-2 и
статистика работают автономно. В Release 3 нужно добавить анализ ответов,
проверку карточек и генерацию предложений, не превращая LLM в источник истины и
не связывая доступность приложения с доступностью модели.

Спецификация перечисляет несколько возможных провайдеров, но Release 4 отдельно
выделяет облачные интеграции. На машине разработки уже установлен Ollama и
доступна локальная модель `qwen3:4b`. Поэтому первой реализацией будет только
локальный провайдер, а граница провайдеров должна позволять добавить облачные
адаптеры позднее без изменения сценариев.

## Решение

### 1. Ollama — единственный провайдер Release 3

Release 3 реализует интерфейс провайдера и один адаптер Ollama. Groq,
OpenRouter, Cerebras, автоматическое переключение и квоты облачных тарифов не
входят в релиз. Это исключает преждевременную работу с нестабильными тарифами,
региональными ограничениями и передачей пользовательских ответов третьим лицам.

AI явно включается настройкой. Отключённый или недоступный Ollama не мешает
запуску Backend, health core-сервисов, CRUD, Review Engine и статистике.

### 2. Провайдер не знает о карточках и базе данных

Общий асинхронный интерфейс провайдера принимает:

- системную и пользовательскую части запроса;
- JSON Schema ожидаемого результата;
- параметры генерации и технический тип сценария.

Он возвращает:

- проверенные структурированные данные;
- фактические имя провайдера и модель;
- число входных и выходных токенов;
- длительность и технические метаданные вызова.

Адаптер не открывает SQLAlchemy-сессии и не знает сущности `Card`,
`AnswerAttempt` или `AiSuggestion`. Получение доменных данных, построение prompt
и сохранение результата принадлежат сценарию и сервисному слою.

```text
router -> scenario service -> prompt + Pydantic result schema
                    |
                    v
             provider manager -> provider protocol -> Ollama HTTP API
                    |
                    v
             persistence + usage log
```

### 3. Прямой HTTP-клиент вместо SDK

Адаптер использует уже установленный `httpx` и Ollama HTTP API. Дополнительный
Python SDK не нужен: официальный `/api/chat` принимает `format` как JSON Schema,
а ответ содержит счётчики обработанных и сгенерированных токенов. `/api/tags`
используется для проверки доступности настроенной модели.

Запрос выполняется без streaming, с явным timeout, ограничением размера ответа,
низкой температурой и отключённым thinking там, где модель это поддерживает.
Скрытых повторных запросов нет: повтор может увеличить время работы и расход
ресурсов. Решение о повторе принимает пользователь.

### 4. Структурированные ответы обязательны

Каждый сценарий определяет строгую Pydantic-модель результата. Её JSON Schema
передаётся в Ollama, а содержимое ответа повторно проверяется через Pydantic.
Невалидный, неполный или слишком большой ответ считается ошибкой провайдера и
не сохраняется как успешный анализ.

Свободный текст модели не используется для изменения данных. Prompt имеет
версию, а пользовательский текст передаётся как данные с явными границами, а не
как системная инструкция.

### 5. Сценарии независимы

Вместо автономных агентов создаются обычные прикладные сценарии:

- Answer Evaluator;
- Card Analyzer;
- Card Generator.

Они используют общий provider manager, но имеют отдельные входные данные,
prompt, выходные схемы и правила сохранения. Adaptive Tutor и формальное
определение слабых тем остаются в Release 4.

### 6. AI-сущности добавляются вместе со сценарием

Не создаётся универсальная таблица «на все будущие ответы». Миграции появляются
последовательно:

- `ai_requests`, `answer_evaluations` и `ai_usage_logs` — с Answer Evaluator;
- `card_analyses` — с Card Analyzer;
- `ai_suggestions` — с Card Generator.

Результаты анализа неизменяемы и связаны с исходной сущностью через `RESTRICT`.
Повторный анализ создаёт новую запись. Для воспроизводимости сохраняются версия
prompt, провайдер, модель и снимок входных данных либо его достаточное
представление.

`ai_requests` хранит состояние пользовательской команды и резервирует ключ
идемпотентности. Один фактический вызов модели создаёт одну запись usage log
даже при ошибке. Успешный результат и финализация request/usage сохраняются в
одной транзакции после завершения внешнего вызова.

### 7. AI не меняет пользовательские данные самостоятельно

- Answer Evaluator не выбирает оценку SM-2 и не завершает повторение.
- Card Analyzer не редактирует карточку.
- Card Generator сохраняет результат как предложение со статусом `pending`.
- Карточка создаётся или меняется только после отдельного подтверждения
  пользователя.

Подтверждение оценки повторения остаётся существующей транзакцией Review Engine
и не включает вызов модели.

### 8. Идемпотентность и параллельные запросы

Команды, создающие анализ или предложения, принимают `Idempotency-Key`. Перед
вызовом модели сервис атомарно создаёт `ai_requests` с fingerprint команды и
состоянием `pending`. Повтор успешной команды возвращает сохранённый результат
без нового вызова модели; параллельный дубль получает `request_in_progress`, а
использование ключа с другим телом — конфликт.

Завершившаяся ошибка фиксируется в request и usage log. Осознанный новый вызов
после такой ошибки использует новый ключ; повтор с прежним ключом не скрывает
ещё один расход ресурсов.

Это защищает от двойного клика и повторной отправки после сетевой ошибки, но не
запрещает осознанно повторить анализ с новым ключом.

### 9. Ошибки и доступность

Provider manager различает как минимум:

- AI выключен;
- Ollama недоступен;
- модель не установлена;
- timeout;
- ошибка Ollama;
- невалидный структурированный ответ.

Пользователь получает стабильный Problem Details code и русское безопасное
сообщение. Исходный ответ модели и внутренние исключения наружу не передаются.
Обычный сценарий повторения остаётся доступен после любой AI-ошибки.

### 10. Конфигурация и данные

Настройки задаются окружением: включение AI, URL Ollama, модель, timeout,
keep-alive и ограничения генерации. В репозиторий не добавляются секреты.
Полные prompts и пользовательские ответы не пишутся в application logs.

Для локального Ollama денежная стоимость равна нулю. Token usage сохраняется как
техническая метрика, а не как основание для платёжных расчётов.

## Проверка решения

- provider protocol тестируется fake-провайдером;
- Ollama adapter тестируется через `httpx.MockTransport`, без настоящей модели;
- сценарии тестируются отдельно от HTTP и Ollama;
- API-тесты подменяют provider manager;
- отдельный opt-in smoke вызывает установленную локальную модель;
- regression tests подтверждают, что AI недоступность не влияет на core API.

## Последствия

Плюсы:

- core-приложение остаётся offline-first и детерминированным;
- сценарии не зависят от конкретного API модели;
- structured outputs проверяются дважды;
- стоимость повторных запросов и изменения данных остаются под контролем
  пользователя;
- таблицы проектируются по фактическим сценариям.

Ограничения:

- в Release 3 нет облачного fallback;
- качество результата зависит от выбранной локальной модели;
- внешний вызов нельзя включить в транзакцию PostgreSQL;
- JSON Schema снижает, но не устраняет смысловые ошибки модели.
