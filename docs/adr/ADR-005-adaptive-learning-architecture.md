# ADR-005: Архитектура адаптивного обучения

- Статус: предложено для Release 4
- Дата: 2026-11-12
- Область: Adaptive Tutor, рекомендации и тематические тесты

## Контекст

После Release 3 приложение хранит детерминированную историю повторений,
письменные попытки и необязательные результаты AI-анализа. Спецификация требует
выявлять слабые темы, повторяющиеся ошибки, рекомендовать дальнейшие действия и
формировать тематические тесты.

Если сразу передать всю историю модели и принять её вывод за решение, результат
будет трудно объяснить, воспроизвести и проверить. Кроме того, пользователи без
Ollama потеряют основную ценность адаптивного обучения. Нельзя также разрешить
наставнику самостоятельно менять карточки или расписание SM-2.

## Решение

### 1. Два слоя адаптации

Первый слой рассчитывает прозрачные учебные сигналы обычным кодом и SQL:

- число повторений и попыток;
- долю успешных и неуспешных оценок;
- среднюю полноту AI-проверок, если они есть;
- количество просроченных карточек;
- дату последней активности;
- объём данных, на котором основан вывод.

Второй слой — необязательный Adaptive Tutor. Он получает ограниченную сводку,
объясняет найденные пробелы и предлагает действия. AI не рассчитывает базовые
метрики и не является единственным источником статуса слабой темы.

### 2. Недостаток данных — отдельное состояние

Новая тема не считается слабой только из-за отсутствия успешных повторений.
Контракт явно различает:

- `insufficient_data` — истории ещё недостаточно;
- `stable` — имеющиеся сигналы не показывают проблему;
- `needs_attention` — один или несколько проверяемых сигналов требуют внимания.

Порог минимального объёма истории и правила статуса фиксируются вместе с API и
покрываются контрольными примерами до реализации вычислений.

### 3. Рекомендация — предложение, а не команда

Сохранённая рекомендация имеет источник, объяснение и жизненный цикл. Её можно
выполнить, отложить или отклонить. Рекомендация может предложить:

- повторить тему;
- разобрать конкретный пробел;
- пройти тематический тест;
- запросить дополнительные карточки через существующий Card Generator.

Принятие рекомендации не завершает повторение и не меняет SM-2. Генерация
карточек по рекомендации по-прежнему создаёт только `pending` suggestions.

### 4. Никаких автономных агентов

Adaptive Tutor реализуется как ещё один типизированный прикладной сценарий над
существующей границей provider manager. Он не получает прямой доступ к БД,
router или инструментам выполнения кода. Сервисный слой выбирает данные,
строит снимок, вызывает сценарий и сохраняет проверенный результат.

### 5. Тематические тесты отделены от SM-2

Тест — отдельная учебная сессия. Ответы и результат теста сохраняются как
практика, но не создают `review_log` и не меняют состояние карточек. В первой
итерации вопросы составляются из существующих подтверждённых карточек. AI может
предлагать дополнительные задания позднее, но они должны пройти предпросмотр
или строгую проверку и не заменяют эталонные данные.

### 6. Снимки и воспроизводимость

Если рекомендация или тест сохраняются, вместе с ними фиксируются достаточные
входные снимки и версия правил либо prompt. Последующее редактирование карточки
не должно менять уже пройденный тест или объяснение ранее выданной рекомендации.

Таблицы добавляются миграциями только вместе с конкретным сценарием. На этапе
расчёта слабых тем отдельная универсальная таблица сигналов заранее не нужна.

### 7. Облачные провайдеры не входят в адаптивное ядро

Adaptive Learning должен полностью работать без облачного API. Подключение
облачного провайдера выполняется отдельным этапом после проверки актуальных
квот, региональной доступности, политики обработки данных и наличия API-ключа.

Передача пользовательского ответа во внешний сервис требует явного включения.
Система никогда не переключается с локальной модели на облачную скрытно.
Допустим только явно настроенный fallback с облачного провайдера на локальный,
поскольку он не расширяет передачу данных третьим лицам.

### 8. Импорт и экспорт — отдельная граница

Резервное копирование и массовый импорт не смешиваются с Adaptive Tutor. Формат
backup версионируется, импорт сначала валидируется и показывает предварительный
результат. Восстановление истории не должно повторно запускать AI или SM-2.

## Инварианты

- базовые учебные сигналы доступны без AI;
- отсутствие истории не равно слабому знанию;
- каждый статус слабой темы объясняется числовыми сигналами;
- AI не меняет Card, ReviewLog или расписание SM-2;
- рекомендация требует явного действия пользователя;
- тематический тест не маскируется под повторение SM-2;
- пользовательские ответы не отправляются в облако без явного включения;
- импорт не выполняет AI-вызовы и не пересчитывает сохранённую историю.

## Последствия

Плюсы:

- адаптация остаётся объяснимой и полезной без модели;
- вычисления можно проверить детерминированными тестами;
- AI работает с минимальной сводкой вместо полной истории;
- существующие гарантии SM-2 и подтверждения данных сохраняются.

Ограничения:

- качественные рекомендации потребуют минимального объёма истории;
- одинаковые слова в AI-описаниях ошибок ещё не означают один и тот же пробел;
- тематические тесты на основе карточек сначала будут проще полностью
  сгенерированных заданий;
- облачные интеграции и переносимость данных увеличат Release 4, поэтому не
  должны блокировать адаптивное ядро.

## Отклонённые варианты

- Передавать модели всю историю и сохранять её свободный вывод как статус темы —
  непрозрачно, нестабильно и не работает без AI.
- Автоматически менять интервалы по рекомендации наставника — нарушает ADR-001.
- Автоматически принимать сгенерированные карточки — нарушает ADR-004.
- Сразу создавать универсальные таблицы для всех будущих типов рекомендаций —
  преждевременно фиксирует ещё не проверенную модель данных.
